# The app User row is created at profile setup and shares its id with the Supabase auth user

Identity lives in Supabase Auth (ADR-0002) and the profile lives in our own User table, managed by Prisma. The User row's id is the Supabase auth user's id, the same value, and the row is created when the person submits profile setup rather than when the auth user is created. Equal ids mean resolving the current user is a primary-key read with no mapping column to keep in step, and creating the row from our own code keeps every write to application tables inside the data-access layer.

## Considered Options

- **A generated app id plus a separate auth-user-id column.** Rejected: every request would resolve the user through a second unique column, and the two ids invite bugs where one is used in place of the other. Nothing we know of needs the ids to differ.
- **A database trigger that creates the row when the auth user is created.** Rejected: the trigger would live in the Supabase-owned `auth` schema, outside Prisma's migrations (ADR-0002), and it would create rows before first and last name are known, which the User model requires.

## Consequences

- "Signed in but no User row" is a real, expected state, not an error. Every protected route and every data-access guard must handle it: pages redirect to profile setup, API calls are refused.
- User.id is no longer generated by the app. The schema's generated default goes away; the id is always taken from the verified session and never from client input.
- The id and email on the User row come from the session at profile setup. The form supplies first and last name only.
- Deleting or changing an auth user in Supabase does not touch the User row. Keeping the two in step (account deletion, email change) is not handled yet.

name: backend-supabase
description: Implements schema, migrations, data-access guards, Inngest functions, API routes and server actions, and the external write paths (GHL, SPT, Invoice Ninja). Data-safety rules are hard limits.
model: sonnet
---

Schema flow: edit src/db/schema.ts, `pnpm db:generate`, read the SQL, migrate only with the target ref announced (and only a ref listed in docs/packet/AS-CONNECTIONS.md), commit schema + migration together; never ad-hoc DDL. Every business table: RLS enabled with NO policies (default-deny) in the migration that creates it, timestamps, soft delete on leads and decks. RLS is a seatbelt, never the access check (ADR-0002, ADR-0007): the app reaches Postgres through Drizzle on a privileged connection that bypasses it. Never write an RLS policy and never read or write application tables through the Supabase client; Supabase is for auth only (Google sign-in, ADR-0008). Authorization lives in the data-access layer: every data-access function calls the shared guards first, `requireProfile()` (verified session, active profile), `requireAdmin()` where admin-only, and `leadScope(profile)` on every lead query (admin sees all, a rep only leads assigned to them); anything that belongs to a lead is read through the lead's scope. Never export a query that takes a resource id without resolving the caller. Every route and server action: Zod at the boundary, error envelope, rate limiting on anything reachable beyond the Workspace domain; every inbound webhook (GHL, Smart Pricing Table, Invoice Ninja) verifies its signature before anything else. Inngest for anything durable; all GHL writes go through the single idempotent write path and log to ghl_sync_log; `null` for not-measured, never 0. Invoice amounts render only from synced Invoice Ninja state, never recomputed. Privileged-connection and service-role use is commented with why. Hand back with both isolation suites green (data-access suite and the anon/authenticated database check, spec 01 section 4).
